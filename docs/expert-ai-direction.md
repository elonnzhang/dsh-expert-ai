# 专家 AI 产品方向与服务规划

> 状态（2026-10-20）：分类咨询、评审、专家团与专家包在线导入都已从本仓库移除，当前代码提供身份层（`expertIdentity` 服务与身份库设置页）、单聊（Chat Panel 与 `@` 专家候选）以及向主 Agent 的 `consult_expert` 咨询工具。智囊团提案 `docs/think-tank-agent-team.md` 也已删除，需要时用 `git show 8164529:docs/think-tank-agent-team.md` 查阅。下文对现有代码的分析（如 `consult_expert_category`、`maxBatchSize`、`consult_expert`）记录的是移除前的状态；产品方向仍作后续参考。

建议将 dsh-expert-ai 定位为 **专家认知与协作服务平台**：汇集公开专家方法、经授权的个人经验和组织案例，连接科研工具与任务流程，支持真实问题分析、多专家协作、实验反馈和经验传承。数字分身承担身份与交流，具体服务通过可检查的交付物和结果评测验证价值。

结合星途材料，科研服务成为优先探索的垂直方向。首个完整服务建议调整为 **科研与技术方案评审**，从问题澄清、证据检查、方案比较推进到验证计划和结果复盘。此前的 AI 方案评审保留为低成本工程验证场景；具体科研领域应由可获得的专家合作、案例和验证条件决定。这个定位与服务顺序属于产品建议，尚未经过需求和付费验证。

如将星途作为业务应用方案，dsh-expert-ai 可以承担专家认知管理、协作运行和服务交付，星途侧承担专家合作、课题组织、科研实训和社区运营。这里描述的是拟议分工，不代表已经建立这些合作关系。

## 六维能力如何落到项目

| 能力维度 | 产品职责 | 当前状态与实施选择 |
| --- | --- | --- |
| 科学模型与计算 | 为定量问题选择模型或计算工具，记录适用范围 | 现有模型配置不能等同于科学计算；按服务接入外部能力 |
| 科研技能与执行 | 检索、分析、绘图、仿真及结果复现 | 复用 Harness 工具体系，逐项适配科研技能及依赖 |
| 科研协作流程 | 调度提出、批评、验证、复盘等阶段 | 已有单次与并行咨询，需增加结构化交接、状态和失败处理 |
| 专家推理方法 | 调用框架、案例、判断标准和反例 | 以 mimeographs 作为公开方法来源，补齐检索、审校和评测 |
| 个人科研经验 | 管理授权内容、访谈、失败经验及本人审校 | 当前没有这套内容生产与验证机制，作为核心新增能力 |
| 群体协作与传承 | 多专家协作、实训、案例复用及版本改进 | 现有智囊团设计可以承接协作，传承与持续改进需要独立建设 |

建议把研发重点放在专家方法、个人经验、协作与传承，计算和执行能力按实际任务集成。六个维度需要相互支持，不能用上层交流体验替代底层计算准确性或实验结果。

期望形成两条相互连接的业务链：专家经验进入可审查的认知资产，再进入任务服务和真实验证；验证后的案例进入科研实训，学习者的实践反馈再形成待审查的新案例。每次循环都产生可追溯的资料或结果。

| 当前能力 | 代码依据 | 对专家服务的意义 |
| --- | --- | --- |

| 外部 Markdown 身份与托管身份文件 | `src/host/identity.ts` | 可以接入上游人物方法正文 |
| 单专家一次性咨询 | `src/host/index.ts` 中的 `consult` | 可从当前任务调用专家，支持传递取消信号和配置模型、工具范围 |
| 按类别并行咨询 | `consult_expert_category` | 已有并发入口，可用于早期多视角实验 |
| 独立对话与持久身份绑定 | `src/client/index.ts`、`src/host/session-binding.ts` | 支持与选定专家持续交流和重启恢复身份 |
| 设置、Chat Panel、会话选择器、输入框点名 | `src/client/` | 已有发现、配置和调用专家的交互入口 |
| 固定团队、协作角色与结构化产物设计 | `docs/think-tank-agent-team.md`（已删除） | 可以沿用现有规划演进服务工作流 |

目前可复用的核心是身份、会话和咨询调度。以下差距会直接影响专业服务的交付：

1. `identityFor` 读取一份 Markdown 正文，`agentIdentity` 去掉 frontmatter；插件没有解析 `SKILL.md` 的触发条件，也没有自动载入其 `references/`。指向专家文件只解决身份接入，不能证明参考资料已被使用。
2. 分类咨询使用 `filter(...).slice(0, maxBatchSize)`，按配置顺序取前几位；尚未根据问题选择成员，也没有角色分工与审查阶段。
3. 分类咨询使用 `Promise.all`。一个成员失败会使工具整体拒绝返回，当前没有向用户保留成功成员结果的部分成功协议。
4. 咨询结果主要是文本，尚未建立声明、证据、假设、分歧与交付物之间的结构化关系。
5. 会话绑定保存 `recordId` 和身份提示词快照。它支持身份恢复，但尚未提供独立的跨会话项目记忆、决策记录和知识更新机制。
6. 单次咨询会传入记录的 `model` 和 `toolFilter`；独立会话创建与绑定没有应用同样的记录级配置。两条路径需要统一服务策略。
7. 独立会话强制只读文件沙箱。需要生成文件的服务应增加受控交付物通道；文件沙箱也不能替代对外部连接器动作的权限约束。

现有测试验证基础逻辑，不验证专家判断质量。已有智囊团文档中的动态组队、能力认证和评测属于后续设计，不能作为已实现功能对外描述。

## mimeographs 能提供什么

上游提供的是由公开资料生成的专家方法包。`SKILL.md` 描述适用问题和思考方式，`AGENTS.md` 提供持续生效的行为指导，`references/` 保存原则、框架、心智模型、引文及来源；部分包还有启发式规则和反模式。生成方式见 [上游 README](https://github.com/K-Dense-AI/mimeographs/blob/a38f5fcad0853be3e98a6cd95d8e6bf8c66f7c7b/README.md)。

这些内容可以用于提出更有针对性的问题、暴露不同取舍、组织分析和解释方法来源。专业能力仍取决于底层模型、任务资料、工具以及结果验证。导入人物名称和提示词不能证明达到本人专业水平。

建议将两类内容分别管理：

- **专家方法**：人物的分析框架、价值取舍、适用领域和历史观点，保留来源与版本。
- **任务事实**：用户项目资料、最新技术文档、运行数据与检索证据，记录时间和出处。

历史观点可以启发今天的决策，今天的事实应由当前资料支持。使用方法时也应允许质疑其适用条件，避免把某个人物的偏好当作所有任务的通用规则。

### 抽查发现的质量限制

Albert Hofman 的来源列表混有 Albert Hofmann、LSD 及其他同名相关页面。这证明来源筛选存在实体混淆，尚不能据此断言最终回答一定错误。启用该包前需要逐条筛选来源，不能把整份来源目录直接当作可信检索库。见 [Albert Hofman 来源列表](https://github.com/K-Dense-AI/mimeographs/blob/a38f5fcad0853be3e98a6cd95d8e6bf8c66f7c7b/mimeographs/albert-hofman/references/sources.md)。

Karpathy 包的上游 critique 给出 6/10，指出视觉、自动驾驶、强化学习的覆盖缺口及内容重复。这是生成流程内的评议，不能视为本产品的能力评分或独立测评。见 [上游 critique](https://github.com/K-Dense-AI/mimeographs/blob/a38f5fcad0853be3e98a6cd95d8e6bf8c66f7c7b/mimeographs/andrej-karpathy/_workspace/critique_skill.md)。

因此，专家目录需要区分“已收录”“已审校”“已通过某项服务评测”。验收应落实到专家能完成的具体任务，不能只对整个人物给一个笼统分数。

### 数字分身的表达方式

建议展示为“Steve Jobs 产品思考助手”“Karpathy AI 工程顾问”等，明确基于公开资料构建。抽查的 [Steve Jobs SKILL](https://github.com/K-Dense-AI/mimeographs/blob/a38f5fcad0853be3e98a6cd95d8e6bf8c66f7c7b/mimeographs/steve-jobs/SKILL.md) 本身也要求应用方法而不冒充本人。

## 三类专家资产及其生产方式

专家来源与专家能力分别记录。下面三类资产可以共同参与任务，不表示固定的质量高低：

| 资产来源 | 主要资料 | 可提供的服务基础 | 必须明确的边界 |
| --- | --- | --- | --- |
| 公开方法型 | mimeographs、公开论文、演讲与访谈 | 方法解释、问题澄清、方案的不同分析视角 | 公开资料生成，不代表人物本人授权或当前意见 |
| 组织经验型 | 机构文档、项目复盘、操作流程与失败案例 | 团队知识复用、工程评审与新人培养 | 组织与项目范围、资料时效、适用条件 |
| 授权个人型 | 本人提供或许可的成果、深度访谈、决策案例 | 个人经验咨询、案例教学和特定任务辅助 | 授权范围、本人审校状态及经过验证的任务范围 |

授权个人型的核心建设工作，是把经验转为可调用、可质疑的案例。建议采用“明确使用范围 → 资料整理 → 案例访谈 → 结构化整理 → 本人修订 → 保留任务评测 → 版本发布”的流程。

访谈应围绕具体决策：当时要解决什么、已知哪些证据、有哪些候选路线、为何放弃其他路线、哪里判断失误、什么新证据会改变选择。成功与失败都要收录，同时保留当时条件，避免用事后结果倒推当时已经知道答案。

一个认知资产单元至少包含问题情境、约束、候选方案、判断依据、适用条件、反例、来源和修订记录。人物口吻是展示信息，不能替代这些结构。也不需要以训练个人专属模型作为初期前提，可以先通过检索和结构化工作流验证价值。

本人认可衡量经验表达是否忠实，同行评议和外部任务验证衡量建议是否有效，两类评价都应保留。授权关系和学术身份本身不能消除模型错误。

## 可以提供的服务

以下是候选产品设计。专家组合表示可尝试的方法来源，尚未证明该组合优于普通模型。

| 服务 | 用户提交什么 | 交付什么 | 候选方法来源 | 建议顺序 |
| --- | --- | --- | --- | --- |
| 专家方法咨询 | 一个具体困惑及背景 | 关键追问、方法解释、适用边界和行动建议 | 公开方法包与已审校案例 | P0，低成本入口 |
| 科研与技术方案评审 | 课题、方案、约束、已有证据 | 主要问题、路线比较、证据缺口与验证计划 | 领域专家加方法专家 | P0，首个完整服务 |
| 实验设计与结果复盘 | 假设、数据、设计或实验结果 | 对照条件、可复现步骤、失败解释和下一轮计划 | 相关领域经验与因果分析方法 | P1，按领域验证 |
| 跨学科专家会诊 | 存在多种机制或工程取舍的问题 | 独立意见、冲突来源、可区分观点的实验 | 固定跨领域团队 | P1，复用评审流程 |
| 青年科研实训 | 学习目标、案例作答与实践结果 | 分阶段练习、判断反馈、能力变化和迁移任务 | 专家案例加教学方法 | P1，小范围试点 |
| 专家经验资产建设 | 本人或组织提供的案例、访谈与资料 | 可审校的经验库、评测集和版本化专家实例 | 授权个人及组织合作 | 与服务试点并行 |
| 机构科研知识服务 | 项目档案、流程、成员经验 | 团队答疑、课题复盘、方法复用与人才培养 | 机构自有资产加共享方法 | P2，机构试点 |
| 专家服务 API 或 MCP | 其他应用提交的任务与资料 | 结构化咨询、评审或团队结果 | 同一服务运行时 | P2，作为交付渠道 |

专家咨询可作为早期体验入口；持续使用更可能来自用户反复需要完成的工作，例如每次方案评审都能查出遗漏、每次学习都能暴露误解。这是需要通过试点验证的产品假设。

圆桌的价值应由不同职责和证据贡献体现。第一轮让成员独立判断，再交换批评，最后保留分歧；多个同底模角色的共同意见不能被当作独立证据。对分歧应区分事实冲突、假设差异、领域适用性和价值取舍，再决定补查资料、设计实验或交给人判断，避免用简单多数投票消除少数意见。

科学研究类专家可先用于研究方法和文献审查。涉及临床判断、投资执行等服务时，需要另外建立相应的专业责任与验证体系，超出此 MVP。

机构服务与科研实训值得作为长期方向验证：团队提供的案例、判断准则、失败记录和实践反馈可以积累项目特色。mimeographs 适合作为方法参考和专家包格式的起点。创业与产品决策仍可作为通用专家平台的扩展服务，但本轮科研方向优先验证方案评审与经验传承。

## 首个 MVP 的具体设计

### 目标用户与核心任务

先选择一个能获得真实案例、领域指导和外部验证结果的小型研究或技术团队。用户已有一份方案，希望明确应该先验证什么、哪些设计可以简化、哪里缺乏证据。若已具备材料、能源等领域合作条件，可以从其中一个窄问题开始；若条件尚未具备，先用 AI 系统或计算研究方案验证相同流程。

服务名称建议为“科研与技术方案评审”。用户提交目标、方案资料、已有结果、资源约束和最担心的问题。系统补问影响结论的缺失信息，再展示成员及职责。首轮固定问题澄清、领域分析、独立批评与综合报告四种职责，允许少量成员兼任。

建议首轮配置 3 至 5 个经过内容审查的专家实例和 2 至 3 项必要技能，以完成一条检索、分析、评审和报告链路为准。公开方法与真实领域经验可共同使用，缺少相关领域知识时应缩小服务范围。

在 AI 技术方案验证场景中，可以继续使用以下 6 位候选专家方法，每次通常只选 2 至 3 位：

| 专家方法 | 在首个服务中的职责 | 需要验证的表现 |
| --- | --- | --- |
| Steve Jobs | 用户收益、产品聚焦、体验完整性 | 能把技术描述转成具体用户收益，并提出有依据的范围取舍 |
| Andrej Karpathy | 模型限制、人工验证、实现复杂度 | 能识别自动化过度和验证成本，提出更小的验证步骤 |
| Andrew Ng | AI 项目范围、数据条件、实施路径 | 能根据任务和数据条件提出可执行实验 |
| Jeff Dean | 系统约束、性能、工程权衡 | 能指出需要实测的瓶颈，避免无数据的性能承诺 |
| Judea Pearl | 因果假设和实验有效性 | 能区分相关性、干预结论和未经验证的假设 |
| Socrates | 定义澄清与隐含假设 | 能提出少量关键追问，并推动任务完成 |

这些是拟定的职责与验收目标，需要在所选包的覆盖范围内评测；人物履历不能替代验收。

### 一次服务如何完成

1. 明确问题与验收标准，建立一份任务简报。
2. 根据用户资料和具体问题选择专家，记录选择原因。
3. 各专家使用同一版本的任务资料独立分析，按需读取参考内容或调用已接入的科研工具。
4. 审查者核对关键主张、反例和缺失证据，要求无法支持的结论降级为假设。
5. 汇总交付报告，保留有意义的分歧，并给出下一步验证任务。
6. 用户补充计算或实验结果后，更新报告和决策记录，标明哪些判断发生变化。
7. 将有复用价值的过程提交为候选案例，经审校后用于后续服务或实训，并保留项目原始记录。

默认限制轮次、调用预算和超时。停止任务后禁止继续派发新工作；成员失败时展示部分结果及缺失项。上述运行控制是待实现要求。

### 交付物长什么样

以 AI 技术验证场景中“使用多个 Agent 自动处理客户工单”的方案为例，报告应该回答：

- 用户真正需要缩短哪个处理环节，成功如何衡量？
- 哪些工单适合自动处理，哪些需要人参与？
- 相比单 Agent 或规则流程，多 Agent 带来什么可验证收益？
- 哪些结论来自用户数据，哪些来自方法框架，哪些仍是假设？
- 哪些错误会导致方案失败，如何用小规模实验提前发现？
- 下一步实验需要什么数据、由谁确认、在什么条件下继续或停止？

报告结构建议固定为：任务摘要、主要发现、依据与假设、专家分歧、候选方案、验证计划。每条主要发现关联资料位置或来源；专业框架的来源只支持方法归属，不自动支持它对当前项目的预测。

科研课题沿用同一结构，并明确区分文献依据、模型预测、计算结果和实测结果。把假设写成方案并不代表完成科学验证，报告应指明验证目前进行到哪一步。

### 如何证明服务有效

先整理 30 至 50 个真实或脱敏方案作为试点评测集，覆盖资料缺失、问题含糊、专家领域不匹配和方案本身合理的情况。这个数量是启动建议，不构成统计充分性的保证。

比较三种配置：普通助手、使用相同资料和任务流程的通用评审助手、加入专家方法的评审助手。控制底层模型、可用工具与预算，尽量区分收益来自资料、流程还是专家方法。

评审者在不知道配置名称的情况下检查重大问题发现、事实错误、建议可执行性和冗余度。同时记录任务完成率、引用是否真正支持主张、耗时、成本，以及用户是否继续用报告推进下一步。

只有当专家方法对特定任务表现出稳定增益时，才扩大该服务的专家池；没有增益的角色应简化或移除。第一阶段不以专家数量或发言次数作为成功指标。

对于授权个人型，再分别评估本人对表达的认可、同行对判断的评价，以及建议在真实任务中的结果。这几项可能不同：忠实呈现某人的取舍，不保证该取舍在新条件下仍然正确。前瞻判断应记录提出时间、条件、结果和修订，不能用权威身份代替长期验证。

## 群体协作与传承的最小闭环

建议把“传下去”落实为案例教学和实践迁移。导师将一个真实决策拆成阶段，学习者先判断并解释依据，再查看专家当时的选择和后续结果，最后完成一个条件不同的新任务。

小规模试点可围绕一个研究组或一门实践课程展开，按以下顺序运行：

1. 从经过审校的成功与失败案例中提取问题、证据和关键取舍。
2. 学习者独立提交假设、方案与验证标准，保留初始作答。
3. 专家助手针对遗漏条件和论证缺口反馈，必要时调用方法或计算工具。
4. 学习者实施可行的验证，记录支持、反驳或无法判断的结果。
5. 领域导师复核有价值的发现，再将可共享部分整理为新案例。

评价重点包括独立提出问题、识别证据不足、设计对照、解释失败和迁移到新问题的表现。采用无助手的前后测与延迟迁移任务，观察学习者是否形成能力；对话时长、提问量和满意度只能作为辅助信息。

持续改进应区分四种更新：项目事实变化、专家案例增加、任务流程调整和底层模型训练。前几种可以先通过检索内容及配置版本实现，不必直接训练模型。社区贡献进入待审查区，经过来源检查、专家复核和回归评测再发布；学习者的猜测或模型自己的赞同不能自动升级为专家知识。

每次发布记录谁贡献了什么、适用哪些条件、哪些证据支持或反对、影响哪些服务。遇到回归时能回退内容或流程版本。私有项目资料是否进入共享案例，由其可共享范围决定，不因参与社区而自动公开。

## 工程演进建议

### 专家包与用户配置

保留现有 `ExpertRecord` 作为用户启用和配置的实例。新增独立的专家包描述，记录来源仓库、提交版本、专家标识、原始文件、中文展示信息、引用索引和审校状态。上游包保持版本化，用户定制放在单独的覆盖层，避免更新时覆盖用户修改。

导入过程可以复用 `catalog.json`，按专家下载指定文件，保留相对目录与来源关系。默认不载入生成过程的 `_workspace/`；需要调查质量问题时再查看其中的审查记录。头像按需加载，文本规模目前不要求先建设复杂的向量数据库。

上游四个类别可先映射到现有 `business`、`culture`、`tech`、`science`。保留原始类别用于追溯，服务能力另行记录。分类与标签帮助发现专家，不能授予工具权限或证明服务能力。

导入功能要处理固定版本、文件清单校验、重复 ID、相对路径和更新差异。外部 Markdown 按已审查的方法内容使用，文件中的操作建议不能自行改变权限或执行安装命令。

授权与来源信息不宜继续塞入 `persona` 或 `tags`。建议独立记录来源类型、允许用途、内容审校者、版本和已验证任务。授权状态与能力状态分开管理：内容得到授权不等于某项服务已经通过评测。

### 科研技能适配

科研技能应建立单独的绑定关系，声明依赖包、数据连接、必要凭证、输入输出和执行环境。导入 `SKILL.md`、运行环境可用、执行成功、结果有效是四个不同状态。

第一期只接入所选服务需要的检索与分析技能，保存执行日志和产物。统计或仿真结果关联输入数据、参数和版本；工具失败时报告明确的缺失步骤，不用自然语言补出看似完成的实验结果。具体外部技能及其许可在接入时逐项核对。

### 参考资料与证据

增加限定在专家包范围内的参考资料读取能力，或由 Host 检索后将命中片段交给专家。先从标题、关键词和明确引用查找开始，再根据实际召回问题决定是否增加语义检索。

每条证据应能追溯到专家包版本、文档路径、原始来源及被引用片段。`src_014` 这类局部来源 ID 需要加专家和版本命名空间，避免不同包的来源互相混淆。原文引述、中文翻译、摘要和模型推断应分别标识。

对于最新技术或项目事实，使用当前检索和用户资料补充。不能因为专家包列有某个链接就声称已经读取或验证了该链接。

### 服务与运行记录

建议明确以下对象，按需逐步增加存储，先不引入通用工作流平台：

| 对象 | 负责什么 |
| --- | --- |
| `ExpertPackage` | 方法内容、来源、版本和质量状态 |
| `ExpertRecord` | 用户启用实例、展示与运行配置 |
| `CognitiveAsset` | 经整理的框架、判断标准、经验案例、适用条件和授权来源 |
| `SkillBinding` | 某服务可调用的技能、依赖、权限和执行环境 |
| `ServiceTemplate` | 任务入口、输入要求、角色、输出格式和验收标准 |
| `ServiceRun` | 本次资料快照、成员、状态、预算、失败与取消 |
| `Artifact` | 报告、发现、证据、修订与后续行动 |
| `ProjectMemory` | 经用户确认的项目事实、偏好、决策及其变化 |
| `LearningRecord` | 实训作答、反馈、实践结果及学习迁移表现 |

这些是概念职责，第一期可以用简单文件和明确关联实现所需部分。运行记录关联计算或实验结果，认知资产关联来源和反例；后续增加专用表或图结构应由查询需求驱动。

可在现有咨询工具上增加结构化输出，结合 Harness Provider 实际支持的 `outputSchema` 能力和 Host 验证。一次咨询成功不应只意味着“返回了非空文本”。

身份提示词、模型、工具范围和专家版本应在单次咨询、独立会话与团队任务之间一致解析。运行记录固定本次使用的版本；新包上线后，历史报告仍应能解释当时的依据。

现有只读对话模式可以保留。生成报告时由专门的交付物能力写入受控目录；代码修改或外部执行作为后续明确的服务能力接入。

### 用户体验

首页优先展示“评审研究方案”“设计验证实验”“复盘失败结果”“参加科研实训”等任务。专家卡展示适用问题、可交付内容、来源类型、审校与能力验证情况。已授权的个人实例和公开资料方法助手应能被用户清楚区分。

运行时展示正在进行的步骤和当前交付物。用户可查看专家的独立报告与分歧，无须阅读所有中间发言。现有顶部选择器受开发者工具开关控制，面向普通用户的服务入口应有稳定的可见路径。

### 项目记忆与专家方法

长期记忆优先保存项目事实、已尝试方案、决策原因和待验证问题。不要将用户的临时陈述自动写回专家方法包。项目之间的资料应保持隔离，用户能查看、更正和删除记忆。

这一层更可能支撑持续服务：同一位用户回来时，系统知道上次建议是否执行、假设是否被推翻，以及接下来应验证什么。它需要独立实现，现有身份持久化尚未提供这些能力。

## 实施顺序与完成条件

| 阶段 | 范围 | 完成条件 |
| --- | --- | --- |
| 第一阶段 可验证服务 | 3 至 5 个专家实例、必要科研技能、固定角色与方案评审报告 | 能用真实方案完成服务，读到参考资料、记录工具结果、检查证据与分歧，失败与取消可解释 |
| 第二阶段 经验资产 | 与一位合作专家或一个研究组整理案例，建立本人审校和保留评测集 | 能区分公开方法与授权经验，并验证新增经验带来的任务收益 |
| 第三阶段 协作验证 | 跨领域成员、分歧分类、计算或实验回流、项目记忆 | 能解释结论如何被新结果支持或推翻，并与单专家基线比较 |
| 第四阶段 科研实训 | 案例练习、导师复核、学习记录、迁移评估 | 学习者在独立任务中表现改善，贡献经过审查后可复用 |
| 第五阶段 机构与社区 | 机构实例、版本发布、贡献归属、API 或 MCP | 持续维护质量，按真实使用需求扩展共享和部署范围 |

第一阶段即可建立同模型、同资料与相近预算的对照评测；后续阶段继续使用，避免到生态扩张后才检查效果。各阶段允许小范围并行，但只有满足相应验收才能对外声称该能力可用。

第一期保留现有 Harness 插件形态，有利于复用部署、会话与工具生态。完整 SaaS 的账户、计费、租户管理和运营体系可在需求得到验证后再规划。

商业化优先验证三类需求：研究组按任务或持续使用方案评审服务；机构为自有知识和专家经验的整理、部署、维护付费；人才培养项目为案例实训和学习反馈付费。对每类分别验证实际采购方、使用频率、维护成本和成效，不能以政策方向替代付费证据。

专家目录可以广泛收录，正式服务按质量逐步开放。长期可积累的优势包括持续的专家合作、难以从公开资料获得的失败案例、真实任务反馈、可复用技能适配与学习成效。它们需要通过运营和验证逐步形成。

## 与现有规划的衔接

沿用智囊团提案（已删除，见文首说明）的角色、交接协议、固定团队和人工最终决策设计。先补齐专家包来源、科研技能适配、证据读取和单项服务验收，再推进动态组队、实训和社区更新。

下一步可拆成五项工作：专家资产来源与版本管理、参考资料读取与引用、必要科研技能适配、科研与技术方案评审模板、对照评测与案例采集规范。先证明真实问题中的判断与执行收益，再用实验回流和学习迁移证明协作与传承价值。
